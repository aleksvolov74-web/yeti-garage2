# Yeti Garage — MASTER PROJECT RULES

Этот файл — источник истины по рабочей схеме проекта Yeti Garage.
Если новый чат касается Yeti Garage, сначала читать этот файл и CURRENT_STATE.json.
Не заставлять пользователя повторять эти правила.

## 1. Проект

Приложение: Yeti Garage
Автомобиль: Škoda Yeti 5L
Модельный год: 2011
Двигатель: 1.2 TSI CBZB
Привод: FWD
Коробка: DSG7 / 0AM-DQ200
Репозиторий: aleskvolov74-web/yeti-garage2
Основная ветка: main

Логика каталога:
автомобиль → система → узел → деталь.

2D-технический каталог сейчас приоритетнее полноценного 3D.
Изображения нужны для рабочих экранов каталога, маркеров, карточек деталей, поиска и диагностики, а не как декоративные картинки.

## 2. Жёсткие правила работы

1. Magnific НЕ ИСПОЛЬЗОВАТЬ вообще.
2. Для технических визуалов использовать встроенную генерацию изображений ChatGPT.
3. Каждое сгенерированное изображение ВСЕГДА сразу показывать пользователю в чате.
4. Не генерировать пачку тайком и не упаковывать её до визуальной проверки.
5. Один node_id = один отдельный технический экран.
6. Не делать 3×3 коллажи, инфографики с несколькими узлами или картинки с подписями, если пользователь отдельно этого не попросил.
7. Не путать красивую автомобильную картинку с техническим экраном каталога.
8. Плохая или сомнительная генерация в пакет не идёт — её нужно переделать.
9. Пользователь не должен вручную раскладывать WebP/manifest по проекту.
10. Финальный batch должен быть готов к интеграции And Code целиком.

## 3. Перед каждой генерацией

Сначала:
- прочитать актуальный main;
- найти реальные node_id и part_id;
- проверить текущую версию/versionCode/counts;
- проверить, какие узлы уже имеют изображения;
- проверить сервисную архитектуру именно Yeti 5L;
- учитывать CBZB / DQ200 / FWD / MY2011;
- определить детали, которые реально будут видны на экране;
- заранее определить, какие part_id получат маркеры.

Если точное исполнение зависит от PR-кодов, VIN, комплектации, ревизии, рынка или опции — не фантазировать точную конфигурацию.

## 4. Требования к техническим изображениям

Каждый экран:
- отдельный файл;
- тёмный фон в едином стиле Yeti Garage;
- реалистичный technical/exploded view;
- без людей;
- без текста и встроенных номеров;
- без декоративной инфографики;
- детали должны быть достаточно крупными для телефона;
- композиция должна позволять ставить маркеры;
- показывать только детали данного узла;
- архитектура должна соответствовать Yeti, а не «обычному SUV»;
- никаких невозможных креплений, дубликатов, лишних деталей и AI-артефактов.

После генерации:
- сразу показать изображение пользователю;
- самостоятельно проверить архитектуру;
- при ошибке переделать;
- только принятый вариант конвертировать в WebP и использовать в batch.

## 5. Verification status

VERIFIED_ARCHITECTURE:
архитектура узла подтверждена документацией, но это не означает VIN-exact геометрию или конкретный OEM revision.

REFERENCE_ONLY:
исполнение зависит от PR-кодов, комплектации, VIN, рынка или точной ревизии.

Нельзя самовольно повышать REFERENCE_ONLY до VERIFIED_EXACT или аналогичного утверждения.

## 6. Маркеры

Маркеры создаются только ПОСЛЕ финального изображения.

Требования:
- каждый marker указывает на реально видимую деталь;
- x/y строго в диапазоне 0..1;
- номер внутри node_id уникален;
- part_id реально существует или создаётся как нормальная сущность;
- никаких dummy / placeholder part_id;
- координаты не ставить «примерно по смыслу».

## 7. Состав готового batch

Пользователю выдаётся готовый комплект:
- финальные WebP;
- manifest JSON;
- SOURCES.md;
- SHA256SUMS;
- ZIP;
- готовый детальный prompt для And Code.

ZIP должен содержать всё, что нужно для интеграции.

## 8. Prompt для And Code

В prompt обязательно указывать:
- точное имя ZIP;
- точный путь ZIP на телефоне, например /sdcard/Download/<batch>.zip;
- текущий main/version/versionCode;
- текущие counts;
- автомобиль;
- список node_id;
- статусы каждого node;
- точные part_id;
- новые part_id и русские названия;
- marker count по каждому node;
- ожидаемые images_added / markers_added / totals;
- UI checks;
- regression checks;
- validation/build sequence;
- формат финального отчёта.

And Code запрещено:
- проводить новый глобальный аудит;
- искать другие картинки;
- генерировать свои изображения;
- менять предоставленные WebP;
- перерисовывать их;
- менять архитектуру каталога без требования manifest;
- делать промежуточную APK-сборку до полной интеграции;
- придумывать dummy/placeholder детали.

## 9. Проверка интеграции

Для каждого нового экрана проверить:
- image load;
- zoom;
- pan;
- reset zoom;
- show markers;
- hide markers;
- tap marker;
- select list row;
- marker/list synchronization;
- part card;
- back navigation;
- поиск новых деталей.

Новый экран не должен показывать «Изображение готовится».

Не ломать ранее готовые разделы:
- двигатель CBZB;
- DQ200;
- подвеска;
- рулевое;
- тормоза/ABS;
- впуск/топливо/охлаждение/выпуск;
- климат;
- электрика/освещение.

## 10. Build workflow

Только после полной интеграции:
1. git diff --check
2. Godot import
3. catalog validation
4. startup smoke-check
5. visual catalog smoke-check
6. Android export
7. повысить version ОДИН РАЗ
8. повысить versionCode ОДИН РАЗ
9. commit
10. push
11. GitHub Actions
12. получить APK artifact

Если ожидаемые counts не совпали — этап не считать завершённым.

## 11. Финальный отчёт And Code

Обязательно вернуть:
- images_added
- markers_added
- nodes_with_images TOTAL
- markers TOTAL
- nodes_without_images TOTAL
- new_part_ids
- modified_node_ids
- VERIFIED_ARCHITECTURE total
- REFERENCE_ONLY total
- version
- versionCode
- final commit
- GitHub Actions run
- APK artifact

Также отдельно подтвердить критические правила конкретного batch.

## 12. Поведение в новом чате

Если пользователь пишет:
- «Продолжаем Yeti»
- «Ехала»
- «Что дальше по приложению»
- «Дальше Yeti Garage»

не просить заново объяснять схему.

Сначала:
1. прочитать этот MASTER-файл;
2. прочитать CURRENT_STATE.json;
3. при необходимости проверить актуальный main GitHub;
4. продолжить с текущего незавершённого шага.

Если CURRENT_STATE.json расходится с main, main является источником текущих фактических counts/version, после чего CURRENT_STATE нужно обновить.

Главный принцип:
сначала точность архитектуры → затем отдельный визуал → показать пользователю → проверить → WebP/manifest → ZIP → And Code → validation/build.
